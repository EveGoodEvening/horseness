# ADR 0011: Explicit task execution and reviewed decomposition

## Status

Accepted by user direction on 2026-10-06 and independent planning/security review before source changes. Reopens C22 as a serial pre-publication product correction. Earlier completion evidence remains historical; C23 cannot publish the old candidate as evidence for this correction.

## Context

The daily CLI creates durable draft tasks but has no worker execution path. The protocol registry advertises dispatch operations, while the shipped daemon does not register them. Existing orchestration reducers and host adapters do not by themselves constitute a production task workflow.

## Decision

- Preserve `task add` as draft-only. It never invokes a model, decomposes a task, assigns a worker, or changes canonical revision.
- Add explicit `task dispatch --task ID --adapter HOST`, with optional model selection, plus task detail/result observation. The daemon composes the provider-neutral orchestrator with the selected native adapter. Selecting an adapter and launching one attempt is one operation; a separate pre-assignment command is not introduced.
- Native adapters remain execution bridges, not schedulers or storage writers. Support the existing Pi, OMP, Claude Code, and Codex hosts without silently substituting a host or model. Missing native runtime, credentials, capability, or policy authority fails explicitly before handoff whenever determinable.
- Use the existing durable lifecycle, dependency, ForkPin, context-manifest, immutable binding, launch-intent, authenticated receipt, and task-resolution semantics. Persist launch intent before invoking a host. Unknown outcomes are observable and must never trigger an implicit relaunch.
- Initial receipt-only tasks do not require an unrelated accepted canonical delta to become executable. Canonical-change predicates remain mandatory only where the frozen completion/dependency contract requires them. Worker execution alone never authorizes a canonical mutation.
- The orchestrator derives readiness from current authoritative state and revalidates it at the dispatch transaction. Plan approval or automatic mode does not bypass grants, pinned/current policy conjunction, quota, dependencies, cancellation, or live/unknown attempts.
- `task breakdown --task ID --planner HOST` explicitly launches a planner through the same execution boundary. It produces an immutable, digest-addressed plan preview. It does not adopt the plan or start its execution tasks. Planner output is untrusted data: validate the complete task contracts, unique local identities, dependency references, graph acyclicity, and bounded plan size before presenting an adoptable plan.
- A planner is a separate receipt-only task, not an execution attempt that completes the original objective. The original task remains draft while planning. `task adopt --task ID --plan DIGEST` atomically creates the plan's work tasks and dependencies against the reviewed source task contract. The original task becomes the final integration task, depending on the plan's terminal work nodes; its original completion policy is not silently replaced by a child-count heuristic.
- Plan adoption requires the exact preview digest and matching draft source contract. Adopted plans, child contracts, and dependency graphs are immutable once execution starts. Repeating an exact adoption is idempotent; a changed plan is not an identical retry.
- `task execute --task ID --adapter HOST` runs the target's dependency closure using the same dispatch path. Optional `--auto-plan` explicitly authorizes planner invocation and adoption before execution; the planner defaults to the selected execution adapter unless explicitly selected. The initial executor is serial and deterministic, avoiding concurrent modification of a shared working directory. It stops on failed dependencies, denial, or unknown outcome rather than inventing success or bypassing a gate.
- CLI mutations retain their complete original request, generated IDs, cursor, and idempotency key until a verified result. Background workflow progress is durable and queryable; process restart must expose or reconcile interrupted work without duplicating external effects. Automatic execution is an explicit durable authorization, not a background side effect of adding a task.
- Completion is authority-backed: publish and verify output/evidence bytes before receipt references, authenticate producer and immutable attempt binding, record the first terminal fact, then resolve the task separately according to its frozen policy. Model prose claiming success is not a substitute for a valid receipt. Human-language acceptance criteria guide the worker; they are not represented as automatically verified semantic evidence.

### Execution identity and recovery

Resolve a versioned effective execution profile before committing launch intent: adapter identity, verified native executable identity/digest and version, provider/model, purpose, and bounded non-secret execution options. Bind the profile digest into the immutable prepared attempt/intent and context-manifest sources; receipt provenance must bind that digest and the native-observed host/model. Resolve defaults once, not again on recovery. If a host cannot resolve a default through its supported non-secret interface, require an explicit concrete model instead of claiming an unknown default is pinned. A mismatched or unobservable required native identity/model cannot yield a successful receipt.

Persist the host's actual lookup and launch-idempotency guarantees with the intent. Distinguish found, authoritative absent, unsupported, ambiguous, and lookup error. A missing local record, null result, missing receipt, or lookup exception is not proof of native absence. Same-key replay requires both authoritative absence and a proven host-native idempotent-launch guarantee; otherwise stop at `unknown_outcome`. The new bridge must not reuse the existing null-to-not-found shortcut or `RELAUNCH_IDEMPOTENT` classification without those proofs. Native CLI execution with no such guarantee advertises non-idempotent launch and fails closed after interrupted handoff; an authentic late terminal receipt can still resolve it.

Receipt-only task execution uses the existing adapter receipt-collection contract and does not synthesize a dummy proposal or canonical delta. The existing native `WorkerReturnV1` proposal/decision contract remains required for canonical-change work; a CLI-native receipt-only execution is not claimed as proof of that separate native-contribution loop. Execution policy evaluates the existing rule conjunction against the real intent subject, never a fabricated proposal identity.

### Planner containment and automatic authorization

Planner output is a closed data schema containing only local task keys, titles, instructions, human acceptance criteria, and local dependency keys, with at most 32 work tasks. It cannot choose identities, native executables, provider options, grants, capabilities, canonical roots, policies, completion predicates, or external resource scopes. Adoption is a trusted narrowing transformation: derive child identity and effective authority from the source's explicit authorization intersected with the adopter's current grant. Missing source authority grants nothing. Receipt-only source tasks grant no canonical-write scope; widening requires a separate explicit authority decision, never automatic adoption.

Freeze a versioned workflow authorization with issuer principal/grant and expiry, workspace/run/target contract, selected execution profiles, and an immutable dependency-closure identity. Auto-plan instead initially binds a bounded planning/adoption permission for that exact source contract and the closed schema; adoption atomically binds the resulting exact plan and closure digest before any work launch. Active workflow consent freezes its closure even before the first attempt. Before every adoption and child launch, atomically revalidate that authorization, original issuer grant/revocation/expiry, target state, and current closure, in addition to the child's readiness. Record durable stopped/cancelled/revoked outcomes. Target/workflow cancellation prevents further prerequisite launches after restart; resumption requires a fresh explicit authorization and never silently widens an old one.

Security acceptance includes authority-field injection in an otherwise valid plan, model/host mismatch, changed defaults on recovery, crash after native acceptance before handle persistence, unsupported lookup and late receipt without a second launch, issuer revocation/expiry, target cancellation, and pre-launch graph substitution.

## Compatibility and evidence

New task/execution/plan events are versioned domain contracts with deterministic replay. Existing events and C00/C01 history are never rewritten. Existing initialized workspaces must not silently acquire new grants; provide an explicit authority-controlled upgrade or actionable grant instructions.

Verification must include actual CLI to daemon to native-adapter execution in a disposable external workspace, persisted result observation after restart, exact-request deduplication, dependency ordering, preview/adoption separation, and automatic composition. A deterministic provider may exercise a real native host, but fixture success responses are not native execution evidence. Live subscription evidence is distinct and never claimed without an observed invocation. Run changed-package checks and the ordered C22 candidate gates before marking the correction complete.
