# Codex integration

Horseness supports the digest-verified `@openai/codex@0.144.1-linux-x64` distribution. The executable member is `vendor/x86_64-unknown-linux-musl/bin/codex` with SHA-256 `a96f944d1a596dbfb7fdd84f482be5c50e34b04bb371126840d873e4ebf26902`.

The native bundle is a real Codex plugin named `horseness-codex`. It contributes `.codex-plugin/plugin.json`, `.mcp.json`, an `AGENTS.md` context contribution, the `horseness-worker` skill, and the trusted `horseness-worker` MCP server. For pinned Codex 0.144.1, `.mcp.json` sets `cwd: "."` so the host resolves the working directory against the installed plugin root while the relative server argument remains valid. The declaration forwards only the three Horseness runtime socket, nonce, and thread-claim variables. Native `plugin/installed` and `plugin/read` must identify the enabled `horseness-codex@horseness-c18` cache record, and every installed manifest, declaration, context, skill, and server byte must match shipped metadata.

Under ADR 0006, the smoke uses the invoking OS user's existing logged-in Codex subscription session. The verified app-server receives a minimal allowlisted environment: verified binary/runtime `PATH`, required `HOME`/`CODEX_HOME`, locale, bounded temporary paths, and reviewed nonsecret Codex controls. Secret-shaped names and explicit provider API keys, cloud/CI credentials, and proxy credentials are stripped. Horseness never opens, copies, hashes, exports, logs, or persists Codex authentication state and never runs provider logout. Missing or unusable native authentication without environment credentials fails closed with a stable redacted reason.

`pnpm run host:smoke:codex` acquires and verifies the pinned archive and executable, validates pinned app-server schemas, hashes every shipped and installed contribution, and installs/discovers the plugin through Codex's native marketplace lifecycle. Initial, resume, and fork claims each use a fresh app-server process so the plugin MCP child inherits exactly one claim before startup. Turn input carries both the structured `plugin://horseness-codex@horseness-c18` mention and the verified installed skill. The MCP inventory and completed `mcpToolCall` must both attribute the tool to the installed plugin ID; null or config-override attribution fails closed. Returned thread identities are immutably bound to the exact capability/ForkPin and context.

One model turn emits a real `mcpToolCall` for `mcp__horseness-worker__horseness_worker_return` carrying exactly five bound scenarios. The trusted adapter-kit/SDK return path publishes output and evidence, submits an authenticated receipt and sealed proposal, starts and resumes decision observation, and surfaces `accepted`, `rejected`, `conflicted`, `quarantined`, and `approval_required`. The accepted scenario advances the real authority to revision 1 with document `{ "value": 2 }`.

After that batch the smoke terminates the app-server and adapter runtime, reopens durable retained and thread-binding state in new instances, starts fresh pinned app-server processes with the resume and fork claims, re-verifies native plugin-owned MCP inventory, resumes the same native thread, reconciles/reattaches the original attempt, and forks a distinct native thread bound to the pre-registered second capability.

Native uninstall uses an owner-private file-and-parent-fsynced journal. Its kill switch is checked before every runtime request. Startup recovery idempotently removes native plugin and marketplace discovery before authority revocation, then completes. Crash injections cover kill-switch persistence, internal discovery removal, `discovery_disabled`, and `authority_revoked`; each recovery recreates the app-server/runtime from disk, rejects cached claims, and proves fresh native plugin/MCP/skill inventory is absent. Removing Horseness never logs out or claims to revoke the user's Codex subscription session.

The live receipt is host- and candidate-bound and records only nonsecret provenance, model, command/scenario digests, immutable Horseness bindings, output/evidence/receipt/proposal digests, timing, redaction audit, and terminal reason. It has finite scenario, provider-operation, turn, tool, wall-clock, and byte bounds; ADR 0006 intentionally defines no monetary or token-cost cap.
