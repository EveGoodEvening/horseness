# Codex integration

Horseness supports the digest-verified `@openai/codex@0.144.1-linux-x64` distribution. The executable member is `vendor/x86_64-unknown-linux-musl/bin/codex` with SHA-256 `a96f944d1a596dbfb7fdd84f482be5c50e34b04bb371126840d873e4ebf26902`.

The native bundle is a real Codex plugin named `horseness-codex`. It contributes `.codex-plugin/plugin.json`, `.mcp.json`, an `AGENTS.md` context contribution, the `horseness-worker` skill, and the trusted `horseness-worker` MCP server. The shipped `.mcp.json` is a declarative adapter/installer input: its contribution-relative server path must be resolved to the exact absolute path of the independently verified installed or copied bytes. Codex 0.144.1 does not interpolate a plugin-root token for this path. The live app-server thread therefore receives the supported snake-case `config.mcp_servers` override with that absolute path; no direct MCP call API is used.

Under ADR 0006, the smoke uses the invoking OS user's existing logged-in Codex subscription session. Horseness never opens, copies, hashes, exports, logs, or persists Codex authentication state and never runs provider logout. Missing or unusable native authentication fails closed with a stable redacted reason. Horseness attempt authority remains a separate opaque, least-privilege capability.

`pnpm run host:smoke:codex` acquires and verifies the pinned archive and executable, generates and validates the pinned app-server schemas, independently hashes every shipped contribution, installs and discovers the plugin through Codex's native marketplace lifecycle, and starts a JSON-RPC app-server session with `initialize`/`initialized`. A native thread uses explicit `developerInstructions`, `additionalContext`, and `UserInput` skill/text items. After `mcpServer/startupStatus/updated` reports ready and `mcpServerStatus/list` exposes `horseness_worker_return`, one model turn emits a real `mcpToolCall` for `mcp__horseness-worker__horseness_worker_return` carrying exactly five bound scenarios.

The trusted adapter-kit/SDK return path publishes output and evidence, submits an authenticated receipt and sealed proposal, starts and resumes decision observation, and surfaces `accepted`, `rejected`, `conflicted`, `quarantined`, and `approval_required`. The accepted scenario advances the real authority to revision 1 with document `{ "value": 2 }`. Thread resume retains the original thread identity; thread fork creates a distinct identity bound by an immutable mapping. Both reapply the absolute `mcp_servers` override and explicitly re-mention the skill and exact bound context.

Native uninstall is journaled and recovery-idempotent: durable kill switch, native `plugin/uninstall` plus `marketplace/remove`, Horseness capability revocation, then completion. A real fresh app-server thread must have no Horseness MCP inventory. Removing Horseness never logs out or claims to revoke the user's Codex subscription session.

The live receipt is host- and candidate-bound and records only nonsecret provenance, model, command/scenario digests, immutable Horseness bindings, output/evidence/receipt/proposal digests, timing, redaction audit, and terminal reason. It has finite scenario, provider-operation, turn, tool, wall-clock, and byte bounds; ADR 0006 intentionally defines no monetary or token-cost cap.
